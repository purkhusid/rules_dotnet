# rules_dotnet 0.23.0

## Breaking changes

These are the changes since 0.22.2 that can make an existing setup fail to
build, or build something different, after the upgrade. The commits are in
[v0.22.2...v0.23.0](https://github.com/bazel-contrib/rules_dotnet/compare/v0.22.2...v0.23.0).

### Bazel 9 is required

`bazel_compatibility` is now `>=9.0.0` (was `>=8.0.0`).

rules_dotnet also depends on newer or additional modules, which Bazel's version
resolution may raise in your graph: `bazel_skylib` 1.8.1, `rules_cc` 0.2.19
(previously a dev dependency only) and `icu` 78.2.bcr.2.

### The `dotnet` module extension

- **`dotnet.toolchain` no longer takes `name`, and a build uses one SDK.** Any
  module in the graph that passes `name` (even `name = "dotnet"`) fails
  module resolution. The root-most `dotnet.toolchain` tag picks the SDK for the
  whole build; several named SDKs side by side are no longer possible.
  The `<name>_toolchains`, `dotnet_<platform>` (for example
  `@dotnet_x86_64-unknown-linux-gnu`) and `dotnet_apphost_*` repositories are
  gone. Use `@rules_dotnet//dotnet:resolved_toolchain` instead of a
  per-platform SDK repository.
  ([#571](https://github.com/bazel-contrib/rules_dotnet/pull/571),
  [#574](https://github.com/bazel-contrib/rules_dotnet/pull/574))

  ```starlark
  # Before
  dotnet.toolchain(name = "dotnet8", dotnet_version = "8.0.100")
  use_repo(dotnet, "dotnet8_toolchains")
  register_toolchains("@dotnet8_toolchains//:all")

  # After
  dotnet.toolchain(dotnet_version = "8.0.100")  # or global_json = "//:global.json"
  use_repo(dotnet, "dotnet_toolchains")
  register_toolchains("@dotnet_toolchains//:all")
  ```

- **SDKs are looked up online, and the results are kept in `MODULE.bazel.lock`.**
  The built-in table of SDK versions is gone. The extension downloads
  Microsoft's release metadata and the packs' hashes from nuget.org the first
  time it evaluates, and records them as facts in the lockfile. Setups that run
  with `--lockfile_mode=off`, or without network access, need the lockfile
  checked in (or network access on every evaluation). Mirrors need
  `--downloader_config` rewrites for
  `builds.dotnet.microsoft.com/dotnet/release-metadata` and the nuget.org
  registration endpoints as well. A failed lookup is now an error rather than an
  unverified download.
  ([#593](https://github.com/bazel-contrib/rules_dotnet/pull/593),
  [#620](https://github.com/bazel-contrib/rules_dotnet/pull/620))

- **The SDK must be at least as new as every target framework you build.** The
  targeting, runtime and apphost packs now follow the SDK's version, instead of
  being pinned to the latest patch of each release. Building `net9.0` or
  `net10.0` with an 8.0 SDK now fails with a message asking for a newer SDK.
  Self-contained publishes ship the SDK's runtime patch version.
  ([#559](https://github.com/bazel-contrib/rules_dotnet/pull/559),
  [#593](https://github.com/bazel-contrib/rules_dotnet/pull/593))

- **rules_dotnet now builds its own tools with .NET SDK 11.0.100**, whatever SDK
  you pick (previously 10.0.201). The machines that run the build actions must
  be able to run .NET 11, and if your SDK differs, it is an extra download. A
  module that declares no `dotnet.toolchain` also gets 11.0.100.
  ([#571](https://github.com/bazel-contrib/rules_dotnet/pull/571))

### Paket: `paket2bazel` is replaced by the `paket` extension

`@rules_dotnet//tools/paket2bazel` and the `paket.<group>.bzl` /
`paket.<group>_extension.bzl` files it generated are replaced by a module
extension that reads `paket.lock` directly.
([#558](https://github.com/bazel-contrib/rules_dotnet/pull/558))

Previously generated files still load, but they can no longer be regenerated,
and `nuget_repo` now ignores their `dependencies`, `targeting_pack_overrides`,
`framework_list` and `tools` entries (that information is read from each
package's `.nupkg` instead). Delete the generated files and use:

```starlark
# Before
main_extension = use_extension("//:paket.main_extension.bzl", "main_extension")
use_repo(main_extension, "paket.main")

# After
paket = use_extension("@rules_dotnet//dotnet:paket.bzl", "paket")
paket.parse(
    dependencies = "//:paket.dependencies",
    lock = "//:paket.lock",
)
use_repo(paket, "paket.main")
```

Repository names and labels are unchanged (`@paket.<group>//<package>`). The
Paket CLI can be run with `bazel run @rules_dotnet//tools/paket -- install`.

### Moved and removed labels

- **The toolchain type and `toolchain.bzl` moved to `//dotnet/toolchain`.**
  ([#612](https://github.com/bazel-contrib/rules_dotnet/pull/612))

  | Before | After |
  |---|---|
  | `@rules_dotnet//dotnet:toolchain_type` | `@rules_dotnet//dotnet/toolchain:toolchain_type` |
  | `@rules_dotnet//dotnet:toolchain.bzl` | `@rules_dotnet//dotnet/toolchain:toolchain.bzl` |

- **Fewer config settings in `@rules_dotnet//dotnet`.** The
  `tfm_<framework>_<rid>` settings are removed, and `rid_<rid>` /
  `rid_compatible_<rid>` now exist only for portable RIDs (such as `linux-x64`),
  so a `select` on, for example, `rid_ubuntu.22.04-x64` fails. A
  version-qualified `runtime_identifier` is still accepted and is treated as its
  portable RID. `tfm_<framework>` is unchanged.
  ([#565](https://github.com/bazel-contrib/rules_dotnet/pull/565))

- **`dotnet/repositories.bzl`:** `dotnet_register_toolchains` is removed, and
  `dotnet_repositories` has a new signature (it requires `runtime_version` and
  `runtime_tfm` and no longer has a built-in version table).
  ([#574](https://github.com/bazel-contrib/rules_dotnet/pull/574),
  [#593](https://github.com/bazel-contrib/rules_dotnet/pull/593))

### Rule attributes

- **The `dotnet_toolchain` attribute is removed** from the C# and F# binary,
  library and test rules. It was never read; delete it.
  ([#571](https://github.com/bazel-contrib/rules_dotnet/pull/571))

- **Analyzers and source generators no longer hand their NuGet `deps` to the
  compiler.** Only libraries built in the workspace are loaded beside an
  analyzer. A generator that loads a NuGet package at run time (for example
  Humanizer) must list it in the new `analyzer_runtime_deps` attribute instead,
  or it fails to load and its generated code goes missing.
  ([#609](https://github.com/bazel-contrib/rules_dotnet/pull/609))

- **`csharp_binary`, `csharp_library`, `csharp_test`, `fsharp_binary`,
  `fsharp_library` and `fsharp_test` are now macros** that wrap the rules. The
  rule kind seen by `bazel query` is unchanged, but code that uses them as rule
  objects (for example `inherit_attrs = csharp_binary` in a symbolic macro) no
  longer works.
  ([#577](https://github.com/bazel-contrib/rules_dotnet/pull/577))

### Compilation

- **The default C# language version now depends on the target framework**, as
  in the .NET SDK, instead of being the newest version the SDK knows for every
  framework: 7.3 for `netstandard2.0` and .NET Framework, 8.0 for
  `netstandard2.1` and `netcoreapp3.x`, and the framework's own version from
  .NET 5 on (12 for `net8.0`, 14 for `net10.0`). Code that uses newer syntax
  than that no longer compiles, and `nullable = "enable"` on a
  `netstandard2.0` target fails with CS8630. Analyzers and source generators,
  which must target `netstandard2.0`, are the most likely to be hit. Set
  `langversion = "latest"` (or a version) on the target to keep the old
  behaviour; there is no global flag.
  ([#560](https://github.com/bazel-contrib/rules_dotnet/pull/560))

- **Preprocessor symbols now match the .NET SDK.** .NET Framework,
  `netcoreapp` and .NET 5+ builds no longer define `NETSTANDARD*_OR_GREATER`
  (for example `#if NETSTANDARD2_0_OR_GREATER` was true in a `net8.0` build and
  is now false), and .NET 5+ builds now also define `NETCOREAPP`. Use
  `NET5_0_OR_GREATER`, `NETCOREAPP` and so on instead.
  ([#560](https://github.com/bazel-contrib/rules_dotnet/pull/560))

- **The framework a dependency is built for is chosen as NuGet chooses it**
  (nearest compatible framework, with `AssetTargetFallback`). Previously a
  `net8.0` application could get a multi-targeted library's `net48` build over
  its `netstandard2.0` one; such combinations now pick the compatible
  framework, and incompatible ones fail.
  ([#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

- **NuGet package assets are selected as NuGet selects them**, which can change
  the assemblies and native libraries a build gets: a compatible `ref/` folder
  is compiled against instead of `lib/`, a RID-specific `runtimes/<rid>/lib`
  folder replaces `lib/`, and version-qualified RID folders fold onto their
  portable RID. A package whose `lib/` and `ref/` folders are all for
  frameworks rules_dotnet cannot build for (such as `net8.0-android`, Xamarin
  or portable profiles) used to resolve to nothing and now fails when used.
  ([#567](https://github.com/bazel-contrib/rules_dotnet/pull/567),
  [#601](https://github.com/bazel-contrib/rules_dotnet/pull/601),
  [#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

- **The ASP.NET Core request delegate generator and the configuration binding
  generator are off by default**, as in MSBuild, unless the binary is trimmed
  (published with `native_aot`, or a Blazor WebAssembly app). This includes the
  copy that ships in the `Microsoft.Extensions.Configuration.Binder` package.
  Applications fall back to reflection; set
  `enable_request_delegate_generator = "true"` or
  `enable_configuration_binding_generator = "true"` to keep the generated code.
  ([#629](https://github.com/bazel-contrib/rules_dotnet/pull/629))

### Outputs and running

- **`publish_binary` fails when two files would be published to the same path**
  (for example two first-party assemblies with the same name), where the last
  one used to win silently. Set `out` on one of them.
  ([#568](https://github.com/bazel-contrib/rules_dotnet/pull/568))

- **Two content files mapped to the same destination are an error**, instead of
  the last copy winning.
  ([#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

- **Shared frameworks are collected from dependencies**, including a NuGet
  package's `<frameworkReference>`. A framework-dependent application's
  `runtimeconfig.json` now lists, for example, `Microsoft.AspNetCore.App` when a
  dependency needs it, so the machine running it needs that runtime. A
  `self_contained` publish, or a .NET 5+ binary without `-windows` in its target
  framework that reaches Windows Forms or WPF, fails until the binary declares
  the framework (`project_sdk = "web"`, `framework_references`, or a `-windows`
  target framework).
  ([#648](https://github.com/bazel-contrib/rules_dotnet/pull/648))

- **Embedded resource names changed** where they were wrong: a resource in a
  repository's root package lost its first character (`Lib.ata.txt` is now
  `Lib.data.txt`), packages whose names share a prefix (`a/b` and `a/bc`) cut
  the wrong part of the path, and targets in external repositories lost their
  subdirectories. Code that calls `GetManifestResourceStream` with the old names
  must be updated.
  ([#647](https://github.com/bazel-contrib/rules_dotnet/pull/647),
  [#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

- **`.resx` files in `resources` are compiled**, as MSBuild does, to
  `<root namespace>.<path>.resources`, with culture-specific files in satellite
  assemblies. They used to be embedded as raw `.resx` files.
  ([#548](https://github.com/bazel-contrib/rules_dotnet/pull/548))

- **`winexe = True` now builds a Windows GUI executable** (no console window, no
  standard output) and publishes it with a GUI apphost. It used to have no
  effect.
  ([#648](https://github.com/bazel-contrib/rules_dotnet/pull/648))

- **`runtimeconfig.json` no longer lists `<launcher>.runfiles` as a probing
  path.** The launchers pass it to `dotnet exec` instead, so running the `.dll`
  directly rather than through the launcher no longer finds the dependencies in
  the runfiles tree.
  ([#636](https://github.com/bazel-contrib/rules_dotnet/pull/636))

- **The Windows launchers no longer escape arguments**; they are passed through
  as given.
  ([#630](https://github.com/bazel-contrib/rules_dotnet/pull/630))

- **XML documentation files are no longer in a binary's runfiles.** A program
  that reads them at run time (for example Swashbuckle's `IncludeXmlComments`)
  needs them listed in `data`, for example by listing the library there (its
  default outputs include its XML documentation).

- **`deps.json` and `runtimeconfig.json` are written without indentation**, and
  in `deps.json` `assemblyVersion` is a four-part version or left out, and
  `hashPath` is lower case. Tests that compare these files with checked-in
  copies need updating.
  ([#641](https://github.com/bazel-contrib/rules_dotnet/pull/641),
  [#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

- **`dotnet_tool`:** `bazel run` now runs the tool in the directory it was
  invoked from, tools roll forward to newer major runtimes by default
  (`DOTNET_ROLL_FORWARD=Major` unless already set), and `entrypoint` is matched
  by file name next to the package's `DotnetToolSettings.xml`.
  ([#558](https://github.com/bazel-contrib/rules_dotnet/pull/558),
  [#567](https://github.com/bazel-contrib/rules_dotnet/pull/567),
  [#649](https://github.com/bazel-contrib/rules_dotnet/pull/649))

### Custom rules and toolchains

These only matter if you write rules on top of rules_dotnet's providers or
declare `dotnet_toolchain` targets yourself. The providers in
`//dotnet/private` are not a stable API.

- `dotnet_toolchain` has a new mandatory `os` attribute (`linux`, `osx` or
  `windows`).
- `DotnetInfo.runtime_files`, `csharp_compiler_files` and
  `fsharp_compiler_files` are depsets rather than lists, `runtime_files` no
  longer includes the SDK, and the never-set `apphost_path` and
  `apphost_files` fields are removed.
- `DotnetDepVariantInfo` is removed, `DotnetAssemblyRuntimeInfo.appsetting_files`
  is a depset, and the rules now read new fields
  (`DotnetAssemblyCompileInfo.transitive_internals` and `.target_framework`,
  `DotnetAssemblyRuntimeInfo.content_files`) that hand-built providers must set.
